================================================================================
DOUBLE-APPLIED TRANSFORM ON ATTACK LOADERS
================================================================================

Status   : open, to be fixed in a dedicated branch
Found on : branch `scores` (during the scores refactor), 2026-09-08
Scope    : peepholelib.utils.ptd_wraps / peepholelib.datasets.parsedDataset
           affects every consumer that reads the images (`input_key`) of an
           attack loader: the input-space scores AND CoreVectors.

--------------------------------------------------------------------------------
1. SUMMARY
--------------------------------------------------------------------------------

On loaders produced by an attack inference function, the dataset transform
(Resize + CenterCrop) is applied TWICE to the image: once at parse time, before
the attack runs, and once again every time the sample is read back.

Clean loaders get the transform once. Attack loaders get it twice.

The second application does not change the tensor shape, so nothing raises and
nothing looks wrong. What it does is resample the adversarial image
(e.g. 224 -> 232 -> 224 for ResNet50), which perturbs the attack by an amount
well above a typical L_inf budget of eps = 8/255 ~= 0.031.

In effect, a resize-based defence is silently applied to the adversarial samples
before any input-space score gets to see them.

--------------------------------------------------------------------------------
2. MECHANISM
--------------------------------------------------------------------------------

Step 1 - parse_dataset()
    Copies the RAW image (e.g. CIFAR100 32x32) and label into the parsed PTD.
    No transform involved.
    -> peepholelib/datasets/parsedDataset.py:125-153

Step 2 - parse_inference() with an attack inference function
    a) `_StackedDS` is created and `set_transform(transform)` is called, while
       `self.inf` is still None.
       -> peepholelib/datasets/parsedDataset.py:311-312
    b) Batches are read through that _StackedDS, so the transform IS applied:
       the attack receives correctly transformed 224x224 images.
       -> peepholelib/datasets/parsedDataset.py:351-372
    c) `img_classification_atks` returns 'image': imgs_atk, i.e. the ALREADY
       TRANSFORMED attacked image (224x224). It is written into the inference
       PTD, allocated with the shape of that tensor.
       -> peepholelib/datasets/functional/inference_fns.py:50
       -> peepholelib/datasets/parsedDataset.py:333-341
    d) `stack_inference()` is called only AFTER the loop, so during parsing the
       double application does not yet occur.
       -> peepholelib/datasets/parsedDataset.py:374

Step 3 - load_only() (what every eval script does)
    a) `_StackedDS` is created, `set_transform(transform)` is called AND
       `stack_inference()` is called.
       -> peepholelib/datasets/parsedDataset.py:429-438
    b) `stack_inference()` prefers inference values over original ones:
           self.k_ori = [k for k in s_ori.keys() if k not in s_inf.keys()]
       so on an attack loader 'image' now resolves to the attacked tensor.
       -> peepholelib/utils/ptd_wraps.py:104
    c) `__getitems__` builds the merged dict and then applies self.transform to
       it, unconditionally.
       -> peepholelib/utils/ptd_wraps.py:144
       (same for `__getitem__`, ptd_wraps.py:129)

    => the transform is applied to an image that was already transformed.

Note: string access (`_dss['image']`) bypasses the transform entirely
(ptd_wraps.py:112-118). All image reads in the scores go through a DataLoader
batch or a slice, so all of them DO hit the transform.

--------------------------------------------------------------------------------
3. REPRODUCTION
--------------------------------------------------------------------------------

Uses the real _StackedDS and TransformWrap with fake PTDs:

    import torch
    from peepholelib.utils.ptd_wraps import _StackedDS
    from peepholelib.datasets.functional.transforms import TransformWrap
    from torchvision import transforms

    class Fake:
        def __init__(self, d): self.d = d
        def __len__(self): return len(next(iter(self.d.values())))
        def __getitem__(self, i):
            if isinstance(i, str): return self.d[i]
            return {k: v[i] for k, v in self.d.items()}
        def __getitems__(self, idx): return {k: v[idx] for k, v in self.d.items()}
        def close(self): pass

    tr = TransformWrap(transform=transforms.Compose([
            transforms.Resize((232,232)), transforms.CenterCrop((224,224))]),
            input_key='image')

    n = 4
    raw = torch.rand(n,3,32,32)              # what parse_dataset() stores

    # clean loader: inference PTD has NO 'image'
    clean = _StackedDS(ori=Fake({'image': raw, 'label': torch.zeros(n)}))
    clean.set_transform(tr)
    clean.stack_inference(inf=Fake({'output': torch.randn(n,100),
                                    'result': torch.ones(n)}))

    # attack loader: the stored 'image' is already transformed
    attacked = tr({'image': raw.clone()})['image']        # 224x224
    atk = _StackedDS(ori=Fake({'image': raw, 'label': torch.zeros(n)}))
    atk.set_transform(tr)
    atk.stack_inference(inf=Fake({'image': attacked,
                                  'output': torch.randn(n,100),
                                  'result': torch.zeros(n)}))

    served = atk[0:2]['image']

Output:

    clean  : image from ori -> (2, 3, 224, 224)
    stored attacked image shape: (4, 3, 224, 224)
    attack : image from inf -> (2, 3, 224, 224)      <- same shape, no error
    served == stored attacked image ?  False
    max abs difference introduced   :  0.553

--------------------------------------------------------------------------------
4. WHICH TRANSFORMS ARE AFFECTED
--------------------------------------------------------------------------------

Only a transform that is idempotent escapes the problem. Measured on random
tensors (so the deltas are upper bounds; real images will differ less, but still
on the order of, or above, the attack budget):

    model          1st pass     2nd pass    idempotent   max|delta|
    ------------------------------------------------------------------
    VGG16          (224, 224)   (224, 224)  YES          0.0000
    ResNet50       (224, 224)   (224, 224)  no           0.5645
    ConvNeXt-S     (224, 224)   (224, 224)  no           0.4549
    ViT-B/16       (224, 224)   (224, 224)  no           0.8591
    Swin-B         (256, 256)   (256, 256)  no           0.9383
    MobileNetV2    (224, 224)   (224, 224)  no           0.8591

VGG16 is safe only because its eval transform is Resize((224,224)) alone, and
torchvision short-circuits a resize to the size the image already has. Every
other model uses Resize-to-larger + CenterCrop, which resamples on every pass.

--------------------------------------------------------------------------------
5. AFFECTED SCORES (those reading `input_key`)
--------------------------------------------------------------------------------

Exposed on attack loaders:

    FeatureSqueezingScore     scores/feature_squeezing.py     always
    VIMScore                  scores/vim.py                   always
    DMDBase                   scores/dmd.py                   always
    MahalanobisPlusScore      scores/mahalanobis_plus.py      always
    EPSScore                  scores/eps.py                   always
    DOCTORScore               scores/doctor.py                only if magnitude != 0
                                                              (magnitude == 0 reads
                                                               output_key instead)

Not exposed, they read `fit_key` which is normally the clean train loader
(exposed only if you fit on an attack loader):

    VIM_fit, DMD_base_fit, MahalanobisPlus_fit, EPS_fit

Not exposed, they read `output_key`:

    ModelOutputScore (MSP / MaxLogit / Energy / PE), RelUScore,
    DOCTORScore with magnitude == 0

Not exposed directly, they read peepholes / corevectors:

    ProtoClassScore, CAMLinScore, CAMExpScore, DMDScore, DMDScoreConf, DMDPlus
    -- BUT see section 6, point 2.

--------------------------------------------------------------------------------
6. CONSEQUENCES
--------------------------------------------------------------------------------

1) The two score families no longer see the same input.
   'output', 'pred', 'result' and 'attack_success' were all computed at parse
   time from the CORRECTLY transformed attacked image (inference_fns.py:43-54).
   So the output-based scores evaluate the true adversarial sample, while the
   six input-space scores evaluate a partially cleaned one.
   `auc_fpr` filters samples by 'attack_success' (plots/atks.py:54), so a sample
   flagged as a successful attack may no longer be adversarial by the time an
   input-space score sees it. AUC / FPR@95 numbers are therefore not directly
   comparable across the two families.

2) It is not only the scores. CoreVectors.get_coreVectors() reads `input_key`
   the same way (coreVectors.py:96 and :165), so corevectors -- and hence every
   peephole-based score (MACS, SMRC-lin, SMRC-exp, MRC, DMD) -- inherit the same
   double transform on attack loaders. This is the more consequential path.

3) Any already-parsed corevectors / peepholes computed over attack loaders were
   produced from double-transformed images. A fix invalidates them and they must
   be recomputed.

--------------------------------------------------------------------------------
7. FIX DIRECTION (not implemented)
--------------------------------------------------------------------------------

The fix belongs in _StackedDS / parse_inference, not in the scores.

Option A (preferred): do not transform keys served from the inference PTD.
    In `_StackedDS.__getitem__` / `__getitems__`, apply the transform only to
    the keys coming from `self.ori` (i.e. `self.k_ori`). Keys overridden by the
    inference PTD were produced downstream of the transform by construction, so
    they must be passed through untouched.
    Small, local, and fixes CoreVectors and the scores at once.

Option B: store the attacked image in the raw/original space.
    Would require the attack inference function to invert the transform, which
    is not generally invertible (crop). Not recommended.

Option C: mark, per key, whether the transform has already been applied, and
    let TransformWrap skip those. More explicit but more machinery.

Whichever is chosen: attack-loader corevectors and peepholes must be regenerated
afterwards, and the AUC/FPR tables recomputed.
